# R4.1 本地 AI 运行审计拓扑归因

## 失败拓扑证据

受控 trace 仅在 `HEMATURIA_RUNTIME_AUDIT_TRACE=1` 时启用，且只记录进程、模块、会话和聚合事件字段。失败版真实 release Tauri 完成 3 轮问答后得到：

| 位置 | PID / PPID | moduleInstanceId | providerPresent | eventCount |
|---|---|---|---|---:|
| agent-chat 写端 | `53508 / 52240` | `2f112762-e41b-47e7-96d6-43959927a2cf` | `true` | `1 → 2 → 3` |
| settings/evidence 读端 | `53508 / 52240` | `61d0fd6e-e56c-48c3-9947-c4c51dafdaef` | `true` | `0` |

两端属于同一 sidecar 进程和同一 runtime session，但由动态 route bundle 与 sidecar CommonJS 入口分别加载了 `desktopRuntimeEvidence.js`。旧实现的模块级 `runtimeEvents = []` 因而形成两个数组实例。`desktopPatientEvidence` 没有因 `runtimeSnapshot=null` 提前返回；实际失败点是写端和读端未共享同一事件存储。

旧测试把 agent-chat 写入和 summary 读取放在同一 Node 进程、同一模块缓存中，所以错误地共享了同一个数组并通过。真实 release Tauri 的不同模块实例暴露了该假设。

原始受控 trace 保存在外部验证目录 `D:\HematuriaDesktopTopologyEvidence\R4-Topology-20260802-01`，未提交患者问答、病例标识、prompt、token、secret 或 reasoning。

## 修复合同

- 每次 sidecar 启动生成新的 `runtimeSessionId`。
- SQLite 的 `desktop_runtime_sessions` 和 `desktop_runtime_events` 是唯一跨模块、跨进程聚合权威。
- 最终可见患者回答只写入一个 `local_ai_accepted` 或 `rule_fallback_used` 事件。
- `eventId` 唯一约束保证重复提交只计一次。
- 写入失败增加共享失败计数，并使 `runtimeAuditHealthy=false`；不再静默显示正常的 0/0。
- `/api/desktop/evidence`、复制摘要和导出 JSON 均从同一 runtime session 的 SQLite 聚合读取。
- 导出结构使用固定 allowlist，不含患者问答、病例、认证材料或模型推理。

## 修复后真实 Tauri 证明

全新 SQLite、保留既有 WebView2 用户数据的本地 release 测试版完成 8 轮真实 UI 问答：

- `localAiAcceptedCount=7`
- `ruleFallbackCount=1`
- 合计 `8`
- `cloudRequestCount=0`
- `runtimeAuditHealthy=true`
- 关闭并重新打开设置后计数保持 `7/1`
- 学生端未显示 `answerSource`、`local_ai` 或 `rule_fallback`
- 正常退出后本轮已知 Tauri、sidecar、llama PID 和 llama 监听端口残留为 0

修复后写端与读端仍可拥有不同 `moduleInstanceId`，但都使用 `eventStoreKind=desktop_sqlite`，读端得到 `eventCount=8`。复制摘要已从系统剪贴板重新读取并解析；导出文件实际存在、可计算 SHA-256，且两者均通过禁止字段检查。
